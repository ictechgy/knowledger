# 01. 제품 계약

## 문제와 목표

AI-DLC는 방법론이며 이 제품의 저장 구조를 규정하지 않는다. 이 설계는 DDD로 일하는 조직이 KB·LLM 위키를 AI의 지식 공급원으로 사용할 때, **서로 다른 도메인 해석을 보존하고 합의의 적용 범위를 실행 가능한 상태로 관리**하는 문제를 다룬다.

단일 검색 인덱스에 문서를 모으면 용어가 비슷한 문서들이 함께 검색될 수 있다. 검색 점수는 해당 업무에서 그 정의를 사용할 권한이나 합의 상태를 뜻하지 않는다. 공유 문서가 개정되면 어떤 결정과 AI 작업이 영향을 받는지도 추적할 필요가 있다. 이 제품은 이 위험을 줄이는 설계 가설이며 현재 사용자 효과를 측정한 제품은 아니다.

## 사용자와 책임

| 역할 | 하는 일 | 할 수 없는 일 |
|---|---|---|
| 지식 작성자 | 자신의 context에서 초안·개정 제안 작성 | 다른 도메인을 대신해 채택 결정 |
| 도메인 책임자 | 정의의 의미, 예외, 적용 범위 승인·이의 제기 | 권한 없는 부서 기밀 공개 |
| 공동 업무 책임자 | cross-context 계약의 필요한 이해관계자 지정 | 이해관계자를 몰래 제거하여 승인 우회 |
| 개인 기여자 | 해석·반례·근거를 제안 | 개인 의견을 자동으로 전사 합의로 승격 |
| AI 에이전트 | 정의 추출, 차이·반례·영향·문서 초안 제안 | 승인권 소유, 독자적 공개/정책 변경 |
| 플랫폼 운영자 | 노드·게이트웨이·인덱스 운영 | 운영자라는 이유로 업무 의미 변경 |
| 지식 소비자 | 자신의 권한/context로 현재 또는 과거 지식 조회 | 접근 불가능한 문서의 존재 추측 |

부서 ID(`org-sales`)와 context ID(`sales`, `fulfillment`, `settlement`)는 다르다. 한 부서가 여러 context를 관리하거나 한 context를 여러 부서가 공동 소유할 수 있다. context 경계 변경은 별도 거버넌스 변경이다.

## 합의할 것과 공존시킬 것

예시의 세 정의는 각각 유효할 수 있다.

| context | 주문 완료 | 도메인 소유자 |
|---|---|---|
| sales | 계약 체결 완료 | 영업 |
| fulfillment | 해당 주문의 배송 완료 | 물류 |
| settlement | 해당 주문의 대금 수납 완료 | 정산 |

공동 규칙 `리뷰 요청 시점`은 배송 완료를 사용한다. 수납 상태를 대신 사용하지 않는다. 부분 배송·취소·반품의 예외를 명시한다. 물류·고객 경험 담당자가 이 규칙을 승인해야 한다는 정책을 정할 수 있다. 영업·정산의 정의는 그대로 존재한다.

합의 단위는 **불변 문서 개정본 + context + 불변 business scope + 버전이 고정된 usage scope**다. v1 개정본은 이 범위에 결속하며, 다른 범위에서 재사용할 때는 출처를 참조하는 별도 문서/매핑을 만든다. 지식 문서에는 한정된 개념, 상태 계약, 맥락 간 매핑 또는 업무 규칙을 담는다. 한 문서의 일부만 합의됐다면 문서를 나누거나 별도 합의 문서를 작성한다. MVP에서 문단별 투표는 지원하지 않는다.

이견은 `disputed`로 남길 수 있다. 다른 context의 다른 정의가 있다는 이유만으로 충돌 처리하지 않는다. 같은 scope의 서로 양립 불가능한 규칙, 출처 변경, 경계 간 매핑 불일치만 검토 대상으로 올린다. 실제 의미 충돌 여부는 사람의 검토가 필요하다.

## KB와 LLM 위키

문서가 저장된 제품 형태는 core contract에 영향을 주지 않는다.

- KB adapter는 기존 문서·명세를 개정 제안으로 가져온다.
- LLM 위키 adapter는 AI가 만든 요약·링크·설명도 출처 개정본에 결속된 **초안**으로 가져온다.
- 위키의 현재 페이지는 합의 원장에서 생성한다. 페이지에 작성 context, 사용 scope, 책임 조직, 정확한 개정본, 합의 상태, 이견, 근거와 갱신 영향을 표시한다.
- 원문이 바뀌면 그 원문을 근거로 쓴 요약·매핑·규칙을 재검토 대상으로 표시한다. AI가 기존 합의 문서를 무음 덮어쓰기하지 않는다.
- 기밀 원자료는 공유용 요약을 만들더라도 자동 게시하지 않는다. 공개 담당자가 공유 가능한 내용·근거 표시 범위를 확인한다.

## 사용자 흐름

1. 부서는 기존 private KB를 유지하고 context 소유자와 공유 workspace를 정한다.
2. 작성자/AI가 한 개념의 정의·예외·예시를 private draft로 작성한다.
3. 공개 전 검토에서 channel 참여자와 보존 범위를 확인한다. 게시하면 본문과 이력이 공유 노드에 남는다.
4. 필요한 도메인 책임자들이 **같은 개정본**을 보고 approve/object/abstain 중 결정을 기록한다.
5. 정책의 필수 역할 승인이 충족되면 activation을 제출한다. 커밋 결과가 `VALID`인 경우만 active가 된다.
6. 소비자는 업무 context를 지정해 조회한다. AI에는 이 작업에 적합한 합의문과 권한상 허용된 참고자료만 전달한다.
7. 이견·철회·대체가 생기면 원장과 파생 인덱스에 반영하고 영향받은 실행을 표시한다.

## 화면과 상호작용 계약

| 화면 | 반드시 보여줄 정보 | 주요 동작 |
|---|---|---|
| Context map | 부서와 bounded context의 별도 노드, 소유/공동 사용 관계 | context 선택, mapping 없는 경계 확인 |
| 지식 문서 | 현재 scope·정확한 revision·채택 상태·source kind·책임 조직 | 본문/다른 관점/개정 이력 전환 |
| 합의 검토 | 이전 개정과 diff, 적용 scope, 필수 지정 대표, 이견·예외·근거 | approve/object/abstain, 새 revision 제안 |
| 공개 미리보기 | 채널 참여·운영 조직, 공유될 본문/metadata, 되돌릴 수 없는 보존 범위 | 현재 payload/config에 대한 공개 확인 |
| RAG 응답 | 사용 context와 합의, 인용한 개정본, checkpoint, 참고자료와 규범적 근거의 구분 | 근거 열람, 미합의 항목 질문, historical 모드 전환 |
| 재검토 큐 | 변경된 근거, 영향받는 mapping/요약/run, 사용이 보류된 이유 | 재해석·재승인 요청 |

승인 버튼은 활성화될 결과의 context/scope와 본문 diff를 함께 보여준다. 원장 tx ID 등 내부 정보는 기본 화면의 핵심 업무 판단을 가리지 않도록 상세 증거에 둔다. 아직 합의되지 않은 내용에 초록색 '완료' 표시를 하지 않는다. 실패 시 사용자가 무엇을 고칠 수 있는지 짧게 설명하되 private 제목/본문을 오류로 노출하지 않는다.

## MVP 범위

- 단일 회사의 3개 가상 도메인과 한 공유 workspace를 시작점으로 한다. 실제 조직 규모나 고객군이 검증된 것은 아니다.
- 한 종류의 공유 channel, Markdown 전체 snapshot, 문서별 개정·부서 역할 승인·이의·철회·대체.
- 부서별 private vault는 기존 Git/파일/객체 저장소 중 하나에 연결한다. 자동 전사 스캔을 하지 않는다.
- HTTP API + 얇은 KB/위키 UI + RAG adapter + AI-DLC 단계별 context packet.
- 표준화된 전체 개정본과 의존성, 로컬 실행 manifest, 권한·맥락별 검색.

## 초기 범위에 포함하지 않는 것

토큰/기여도 보상, 공개 permissionless network, 전사 단일 온톨로지 자동 강제, 암호학적으로 지식의 참거짓 증명, 임의 PDF·이미지 원문을 대량 on-chain 저장, 실시간 타이핑 전체를 원장 거래로 기록, 자동 법적 효력 판단, 모든 KB SaaS connector, 기밀을 노출하지 않고 의미 검증까지 하는 ZK 프로토콜.

## 성공을 판단하는 기준

동일 용어의 유효한 세 해석이 보존되고 AI가 업무에 맞는 합의만 선택해야 한다. 기밀 원문·문서 ID가 승인 없이 다른 부서로 넘어가지 않아야 한다. 채택 후 문서를 바꿔도 옛 승인이 새 개정본으로 이전되지 않아야 한다. 누락된 합의를 AI가 추측으로 채우지 않아야 한다. 정본에서 위키·인덱스를 재구축할 수 있어야 한다. 정량 기준과 실험은 [구현 계획](07-DELIVERY-PLAN.md)에 둔다.
